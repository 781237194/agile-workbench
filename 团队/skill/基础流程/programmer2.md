# 基础流程 skill · 高级程序员 B

> 口径来源：`团队/流程.md` 第二部分（现行工作流 2026-11-18 校准）+《团队宪法》+ 项目级 `程序员B/角色卡.md`。
> 冲突时以「流程.md 第二部分 / 宪法 / 角色卡」为准。

## 适用场景
接到开发、缺陷或工具/文档类任务并要落代码/文档与证据时。

## 前置条件
- 已 boot 并持有本项目令牌（`team.mjs boot --role programmer2 --project <项目>`）；
- 已读本人角色卡（boot 必读）；项目铁律**按需读**（开工/接手读一次，不必每轮）；
- 本次动作的边界写清楚（只改自己目录/只动授权文件）；仅被 PM 任务叫到才动。

## 步骤（需求 / 缺陷 / 工具三条流）

**通用（每类都先做）**
1. 先确认「真相在哪」：需求正文/工作流/任务单/队列文件属于哪一层，不凭记忆；不改派生文件、不手改状态 JSON。
2. 只从既有入口读写：正文走 `req write`（写者是分析师）、任务走 `task`、消息走 `send/ack`、缺陷走 `task create --type bug`。
3. 产出落到本角色目录（代码按项目信息的规定目录），同哈希交付、版本递增不覆盖（`实现说明-vN.md` + `代码快照-vN/`）。
4. 用程序可复跑的方式验证（脚本/断言/日志），结论写成「命令 + 通过数 + 退出码 + 被测 HEAD」。
5. 完成回执 + `task done --evidence` 才叫完成；失败立即回报卡点（「需处理 <卡点>」），不静默挂着。

**需求类**：等 Owner 对当前正文落 G3 决定、PM 派单（G5+派单前置检查）后开发 → 提交 → 交测试独立复验（G7）→ 需求 `test_done` → **Owner 本人验收**。
- **我不验收需求**：需求级验收只能 Owner 本人；代管只可代记评审决定，需求验收/迭代/终止一律 Owner 本人（程序 `PROXY_ACCEPT_FORBIDDEN` 硬拦）。
- 需求正文归分析师唯一写者；我不改正文、不评自己写的需求、不催 Owner 点验收。

**缺陷类**：立缺陷单（`type=bug`，带 repro+验收标准）→ PM 派 → 我修并提交（提交信息带缺陷号）→ 测试独立复验（报告+证据两件套）→ **PM 或测试人员 `task accept --as pm|tester` 验收缺陷单**；我作为开发**不自己验收/不代回执**，只提供修复提交与可复跑证据。
- 红线：需求验收≠缺陷验收；任何「需求」的 accept 都不是我的动作。

**工具/文档类**：直接改 + 提交 + tester 确认；跨边界/敏感改动先报 PM 定范围；角色卡/skill 只改自己的（见下「文档维护」）。

## 判据
- 有可复跑证据（命令能重跑、结果一致），不是「我看过了」；写明被测 HEAD、隔离方式、启动 PID。
- 写盘只发生在授权范围内；同名文件用新版本号，旧版保留；报告禁用 `FAIL`/`不通过`/`未通过` 三词（用「未达标项/豁免项/不合格项」）。
- 门禁（G1/G2/G3/G5/G7、证据门）不因本次动作被绕过；验收权限边界不被绕过。
- 回执正文 ≤300 字（消息系统上限 600），含任务 id、产出路径、证据路径；评审意见 ≤600 字。

## 工装与进程安全（P0 硬规）
- 禁止任何脚本/临时命令按进程名/路径/时间窗批量杀 electron（`Get-Process … | Stop-Process`、`taskkill /IM electron.exe`、`pkill`/`killall`）；**只允许** `taskkill /PID <自己 spawn 的 child.pid> /T /F` 或 `child.kill()`；无 PID 不杀。
- 新工装提交前跑 `node scripts/check-no-batch-electron-kill.cjs`，必须 `NO_BATCH_ELECTRON_KILL_OK`；排障优先只读（`Get-CimInstance Win32_Process` 看命令行/启动时间）。

## 测量窗口与隔离
- 真窗口/Electron 测量前先报 PM「需要干净窗口」，测量结束立即停手并回报。
- 隔离三件套：`AWB_DATA_DIR` 独立实例 + `TEAM_ROOT` 沙盘 + `TEAM_SELFTEST=1`；断言真实团队/工作台 sha256 前后不变；记录 HEAD、PID、同时段 electron 进程数/CPU。
- 负载异常（CPU 满/进程数异常）的结果只作观测，不作门禁判据。

## 文档维护分工
- 我的**项目级角色卡**（`项目/<项目>/程序员B/角色卡.md`）可改：改前备份旧版到 `产出/证据-*/` 记录 sha；**改后自己的令牌失效，必须自行重 boot 再继续**。
- 我的 skill（本文件）可改：升版本号 + 旧版归档；按 Owner 2026-11-18 指令 `skill-manifest.json` 不由我改（集中更新），改后跑 `node scripts/skill-check.cjs` 并在回执说明 drift。
- 《宪法》《流程.md》《项目铁律》由 PM 维护（我只读）；角色卡模板/宪法模板/铁律模板由程序员 A 维护；需求正文由分析师唯一写者。

## 反例
- 直接改状态 JSON / 派生文件「图快」，导致账本与真相分叉；
- 只回「收到」不产出、或把回执当成完成；
- 用旧报告/旧截图当本次证据；测例或脚本被改过却不核对 mtime；
- 报「已通过」但给不出重跑命令与通过数；
- 按名称/路径批量杀 electron（会误杀 Owner 生产工作台，已发生两次事故）；
- 自己验收需求或替 PM/测试人员点 accept、代别人回执；
- 未报 PM 就起 Electron 测量，污染别人的干净窗口。

## 换人 / 交接（每角色必读）

- **何时交接**：轮次 ≥ 8 或用量档 warn/force（团队默认阈值）；Owner/PM 明确要求；会话异常（崩溃、OOM、换模型）导致无法继续但任务未收口。
- **交接文件**：`<角色目录>/产出/交接-最新.md`，固定八节（现在状态 / 已收口 / 在途 / 待 Owner 定 / 血的教训 / 关键文件路径 / 接手头三件事 / 全部未完成盘点）；盘点数字必须现查，不抄上一版。
- **回执**：写完后先给 PM 发一条回执（路径 + bytes + sha8 + mtime + 八节齐全 + 手头活是否已收口），由 PM 统一 archive + rotate；**回执不是交接完成本身**。
- **boot**：换人后新会话第一件事 `team.mjs boot` 拿新令牌；名册（团队.json）一改**全员**旧令牌失效，受影响角色各自重 boot。
- **广播**：名册变更后只由 PM **广播一次**「全员重 boot」，其余角色不各自广播、不刷消息；交接内容走文件、不走长消息。
- **失败回滚**：交接文件没写完不 rotate；rotate 失败保留旧绑定并报 PM（不手工改 JSON）；有在途任务时归档是**建议不阻断**（ARCHIVE_DEFERRED），不得为归档丢活；回滚以「旧会话继续干」为默认，不重 claim、不重写报告。
- 角色专属提示（programmer2）：交接时把「当前在办任务 id + 卡点 + 下一步命令」写进「在途」，让接手人不用翻聊天记录即可继续。
