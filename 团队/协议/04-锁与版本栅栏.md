# 04 · 锁与版本栅栏

## 一、为什么两个都要

| 机制 | 防什么 | 防不了什么 |
|---|---|---|
| 锁 | 两个会话同时写同一资源 | 两个会话拿着旧版本各自点头 |
| CAS（哈希栅栏） | 旧版本被批准后覆盖新版本 | 同时写（靠锁） |

**锁只防同时写；版本靠 CAS。** 两个都要。

## 二、锁

```powershell
node 团队\工具\team.mjs lock acquire --boot <T> --key "file:项目:src/a.mjs" --ttl 60 --reason "..."
node 团队\工具\team.mjs lock heartbeat --boot <T> --key "..." --ttl 60
node 团队\工具\team.mjs lock release --boot <T> --key "..."
node 团队\工具\team.mjs lock status
```

- 锁 = `状态\锁\<key>.lock\owner.json`，目录原子创建。
- 过期 / 进程已死 → 可被清理；清理前 `lock status` 看清 holder。
- 不抢别人的锁；`LOCK_BUSY` → 停手报告 PM，不硬等、不删锁。
- 锁 key 约定：`file:<项目>:<相对路径>`、`task:<项目>:<id>`、`apply:<项目>`、`index:<项目>`、`_events`、`_team`。

## 三、版本栅栏（CAS）

- 提案记录每个文件的 `baseHash`（提案时读到的版本）和 `newHash`（新内容哈希）。
- 评审/签字都绑定这两个哈希。
- apply 时重新算目标当前哈希：
  - `current === baseHash` → 通过；
  - 否则 `STALE_BASE`，整单作废，**不写任何文件**。

## 四、典型“旧文件互相点头”场景

1. A、B 都读了 v1；
2. A 提提案 PA（base=v1），B 提提案 PB（base=v1）；
3. A 的提案先 apply → 目标变 v2；
4. B 的提案也拿到签字，但 apply 时 current=v2 ≠ base=v1 → **B 被 CAS 拒绝**；
5. B 必须重新读 v2 → 重提 → 重审 → 重签。

⛔ 不允许“我们是老朋友，签一下就行”；签字只对哈希负责。

## 五、失败与回滚

- apply 中途失败：按备份恢复旧文件、删除新建文件，并核对恢复后的哈希。
- 回滚不完整 → `ROLLBACK_FAILED`，立即停手，人工介入；不许继续写。
- 回滚演练：`team.mjs selftest` 里用 `--fail-after-backup` 真跑一遍。
