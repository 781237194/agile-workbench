# 团队工作流（从需求到收口）

> 这是团队执行顺序，不是建议。PM 必须按闸门推进，不能跳过回执直接叫下一批人。
> **口径唯一来源＝《团队宪法》第 9 条**（2026-11-16 Owner 指令：废除提案互审）；本文件与各项目 `协作准则.md` 是执行说明，冲突时以宪法为准。
> 2026-11-17 更新：删除提案/互审/签字链，改为「产品评审 → TR-Q → Owner 门 → 派开发 → 测试确认 → Owner 验收」。

## 总原则

- 一个工作区 = 一个项目；一个任务只有一个 owner。
- 一次只叫一个角色：`send --ack` 后 PM 停手，等对方 `ack`；未回执不派下一个。
- 没有回执 = 没发生；没有评审结论/测试报告/提交 = 没完成。
- 只读任务需要的文件，不读全目录。
- 每次提交/回执一句话日志（对象 + 动作 + 单号/时间），不写长汇报。

## 阶段表

| 阶段 | 负责人 | 输入 | 动作/产物 | 闸门（必须满足才进下一阶段） |
|---|---|---|---|---|
| 0 接单 | PM | Owner 目标/场景/边界/期限 | 写 `项目信息.md`；建需求/任务；定优先级建议 | Owner 确认目标；项目信息已写 |
| 1 需求 | 需求分析师 | Owner/PM 的任务 | 在 `需求/R-YYYYMMDD-xxxx-标题.md` 写用户故事、边界、验收标准、异常；更新 `需求/00-需求总览.md`；正文只走 `req write` | 需求正文定稿（G1：四件套＋边界六类）；需求行登记 |
| 2 产品评审 | 产品设计师 | 需求正文 | `req review --verdict approve|reject`；打回写清缺什么 | 产品 approve（G2）；打回回阶段 1 |
| 2.5 可测性评审 | 测试人员 | 产品通过的需求 | `req trq --verdict testable|not_testable`（只有测试人员能落） | TR-Q=testable，否则 not_testable 硬拦派单（P0 全档、P1 到 not_testable 也拦） |
| 3 Owner 评审 | Owner（可有效代管代记） | 产品/TR-Q 后的正文 | Owner 在评审弹窗点「通过/打回」或终端 `owner` 落账；PM 记录 | **G3 硬门**：`ownerReview.status=approved` 或 `decisions` 非空，且 basis 绑**当前正文** sha；正文一改旧决定失效 |
| 4 派开发 | PM | Owner 通过 + 需求行 ready | 建 A/B 任务（带 requirementId、目标文件、验收）；一次只派一个 | G5：目标角色无其它未闭环任务；有则先 done/释放 |
| 5 开发 | 程序员 A/B | 任务 + 需求 + 架构 | 直接实现并提交（工具/壳层/脚本/产出类），提交信息带需求号+任务号；产出写 `site/**` 或项目指定代码目录 | 提交存在且可复核；不需要提案/互审/签字 |
| 6 测试确认 | 测试人员 | 提交 + 验收标准 | 独立跑 verify/用例；写测试报告（含需求 id + 结论）与证据；缺陷闭环 | G7：报告存在且结论覆盖该需求；证据两件套（报告 + 截图/记录） |
| 7 Owner 验收 | Owner 本人 | 测试通过的需求 | 评审弹窗或终端 `owner --action accept` | **需求验收只能 Owner 本人**（代管代验收被程序拒绝，`PROXY_ACCEPT_FORBIDDEN`）；缺陷验收走 `task accept`（PM/测试） |
| 8 迭代 | PM | 测试结论/Owner 反馈 | 新需求新建文件；澄清更新原需求（不把新需求塞旧文件）；`req iterate` 才能把打回需求送入下一轮 | 新需求重新走阶段 1；被拒需求不能用 `req reopen` |

## 回执链

```text
Owner → PM：目标/边界
PM → 需求分析师：需求任务
需求分析师 → PM：需求正文 + 回执
PM → 产品：需求评审任务
产品 → PM：评审结论（RR）+ 回执
PM → 测试：TR-Q 任务（复杂需求）
测试 → PM：TR-Q 记录 + 回执
PM → Owner：需求正文 + 产品/TR-Q 结论（路径/摘要）
Owner → PM：通过 / 打回 + 意见（PM 记录并逐条处置）
PM → 程序员 A/B：一次一个开发任务
A/B → PM：ack + claim + commit + 回执
PM → 测试：commit + 验收标准
测试 → PM：测试报告 + 证据 + 回执
PM → Owner：验收材料
Owner → PM/系统：accepted / rejected（只能 Owner 本人）
PM → 下一轮：收口结论
```

## 文件路径纪律

- 所有交付文档必须写在**当前项目目录**内：PM 写 `项目经理/` + 根文档；产品写 `产品/`；需求写 `需求分析师/`；测试写 `测试人员/`。
- 程序员代码写**《项目信息.md》指定的代码目录**（未写默认 `site/**`；本项目为仓库根 `src/**`、`团队/工具/**`），不得写进 `程序员A/` 或 `程序员B/`；角色目录只放设计、交接、回执、索引。
- 禁止写 `%TEMP%`、桌面、C 盘根目录、用户 Home 根目录；临时文件统一放项目 `_tmp/`，交付前删除。
- 发现文件写到项目外：立即停手，报 PM，不得继续提交。

## PM 的硬闸门

1. 没写 `项目信息.md`，不叫角色。
2. 没收到需求分析师的回执（正文定稿），不叫产品评审。
3. 没收到产品评审结论（非 approve）或 TR-Q 不是 testable，不送 Owner 门。
4. **Owner 没对当前正文落决定（G3），不派程序员**；正文改版后旧决定自动失效，必须重落。
5. 目标角色还有未闭环任务（G5），不派新单；先 done 或释放。
6. 没收到测试报告与回执，不把任务标 done；没有证据两件套，不做需求验收。
7. 一次只发一个 `send --ack`；派单锁未清，不派下一个（ack 回执即释放该锁，10 分钟 TTL 兜底）。

## 角色回执格式（一句话）

```text
角色 id + 任务 id + 已完成动作 + 产物/commit + 边界
```

例：

```text
analyst T-... 已完成 R-... 需求正文（R-…-xxx.md 15.2KB/sha 0a1b2c）并回执；边界：未改产品/代码
tester T-... 已复验 commit C-...，3/3 PASS，报告 测试报告-vN.md；边界：未改业务代码
```

## 失败即停

锁冲突、CAS 失败（仅提案类遗留）、评审缺失、测试不通过、回执缺失：停手报 PM，不绕过、不硬试到成功。
