# 团队工作流（从需求到收口）

> 这是团队执行顺序，不是建议。PM 必须按闸门推进，不能跳过回执直接叫下一批人。
> **口径唯一来源＝《团队宪法》第 9 条**（2026-11-16 Owner 指令：废除提案互审）；本文件与各项目 `协作准则.md` 是执行说明，冲突时以宪法为准。
> 2026-11-17 更新：删除提案/互审/签字链，改为「产品评审 → TR-Q → Owner 门 → 派开发 → 测试确认 → Owner 验收」。

## 总原则

- 一个工作区 = 一个项目；一个任务只有一个 owner。
- 一次只叫一个角色：`send --ack` 后 PM 停手，等对方 `ack`；未回执不派下一个。
- 没有回执 = 没发生；没有评审结论/测试报告/提交 = 没完成。
- 只读任务需要的文件，不读全目录。
- 每次提交/回执一句话日志（对象 + 动作 + 单号/时间），不写长汇报。

## 阶段表

| 阶段 | 负责人 | 输入 | 动作/产物 | 闸门（必须满足才进下一阶段） |
|---|---|---|---|---|
| 0 接单 | PM | Owner 目标/场景/边界/期限 | 写 `项目信息.md`；建需求/任务；定优先级建议 | Owner 确认目标；项目信息已写 |
| 1 需求 | 需求分析师 | Owner/PM 的任务 | 在 `需求/R-YYYYMMDD-xxxx-标题.md` 写用户故事、边界、验收标准、异常；更新 `需求/00-需求总览.md`；正文只走 `req write` | 需求正文定稿（G1：四件套＋边界六类）；需求行登记 |
| 2 产品评审 | 产品设计师 | 需求正文 | `req review --verdict approve|reject`；打回写清缺什么 | 产品 approve（G2）；打回回阶段 1 |
| 2.5 可测性评审 | 测试人员 | 产品通过的需求 | `req trq --verdict testable|not_testable`（只有测试人员能落） | TR-Q=testable，否则 not_testable 硬拦派单（P0 全档、P1 到 not_testable 也拦） |
| 3 Owner 评审 | Owner（可有效代管代记） | 产品/TR-Q 后的正文 | Owner 在评审弹窗点「通过/打回」或终端 `owner` 落账；PM 记录 | **G3 硬门**：`ownerReview.status=approved` 或 `decisions` 非空，且 basis 绑**当前正文** sha；正文一改旧决定失效 |
| 4 派开发 | PM | Owner 通过 + 需求行 ready | 建 A/B 任务（带 requirementId、目标文件、验收）；一次只派一个 | G5：目标角色无其它未闭环任务；有则先 done/释放 |
| 5 开发 | 程序员 A/B | 任务 + 需求 + 架构 | 直接实现并提交（工具/壳层/脚本/产出类），提交信息带需求号+任务号；产出写 `site/**` 或项目指定代码目录 | 提交存在且可复核；不需要提案/互审/签字 |
| 6 测试确认 | 测试人员 | 提交 + 验收标准 | 独立跑 verify/用例；写测试报告（含需求 id + 结论）与证据；缺陷闭环 | G7：报告存在且结论覆盖该需求；证据两件套（报告 + 截图/记录） |
| 7 Owner 验收 | Owner 本人 | 测试通过的需求 | 评审弹窗或终端 `owner --action accept` | **需求验收只能 Owner 本人**（代管代验收被程序拒绝，`PROXY_ACCEPT_FORBIDDEN`）；缺陷验收走 `task accept`（PM/测试） |
| 8 迭代 | PM | 测试结论/Owner 反馈 | 新需求新建文件；澄清更新原需求（不把新需求塞旧文件）；`req iterate` 才能把打回需求送入下一轮 | 新需求重新走阶段 1；被拒需求不能用 `req reopen` |

## 回执链

```text
Owner → PM：目标/边界
PM → 需求分析师：需求任务
需求分析师 → PM：需求正文 + 回执
PM → 产品：需求评审任务
产品 → PM：评审结论（RR）+ 回执
PM → 测试：TR-Q 任务（复杂需求）
测试 → PM：TR-Q 记录 + 回执
PM → Owner：需求正文 + 产品/TR-Q 结论（路径/摘要）
Owner → PM：通过 / 打回 + 意见（PM 记录并逐条处置）
PM → 程序员 A/B：一次一个开发任务
A/B → PM：ack + claim + commit + 回执
PM → 测试：commit + 验收标准
测试 → PM：测试报告 + 证据 + 回执
PM → Owner：验收材料
Owner → PM/系统：accepted / rejected（只能 Owner 本人）
PM → 下一轮：收口结论
```

## 文件路径纪律

- 所有交付文档必须写在**当前项目目录**内：PM 写 `项目经理/` + 根文档；产品写 `产品/`；需求写 `需求分析师/`；测试写 `测试人员/`。
- 程序员代码写**《项目信息.md》指定的代码目录**（未写默认 `site/**`；本项目为仓库根 `src/**`、`团队/工具/**`），不得写进 `程序员A/` 或 `程序员B/`；角色目录只放设计、交接、回执、索引。
- 禁止写 `%TEMP%`、桌面、C 盘根目录、用户 Home 根目录；临时文件统一放项目 `_tmp/`，交付前删除。
- 发现文件写到项目外：立即停手，报 PM，不得继续提交。

## PM 的硬闸门

1. 没写 `项目信息.md`，不叫角色。
2. 没收到需求分析师的回执（正文定稿），不叫产品评审。
3. 没收到产品评审结论（非 approve）或 TR-Q 不是 testable，不送 Owner 门。
4. **Owner 没对当前正文落决定（G3），不派程序员**；正文改版后旧决定自动失效，必须重落。
5. 目标角色还有未闭环任务（G5），不派新单；先 done 或释放。
6. 没收到测试报告与回执，不把任务标 done；没有证据两件套，不做需求验收。
7. 一次只发一个 `send --ack`；派单锁未清，不派下一个（ack 回执即释放该锁，10 分钟 TTL 兜底）。

## 角色回执格式（一句话）

```text
角色 id + 任务 id + 已完成动作 + 产物/commit + 边界
```

例：

```text
analyst T-... 已完成 R-... 需求正文（R-…-xxx.md 15.2KB/sha 0a1b2c）并回执；边界：未改产品/代码
tester T-... 已复验 commit C-...，3/3 PASS，报告 测试报告-vN.md；边界：未改业务代码
```

## 失败即停

锁冲突、CAS 失败（仅提案类遗留）、评审缺失、测试不通过、回执缺失：停手报 PM，不绕过、不硬试到成功。

# 第二部分：现行工作流（2026-11-18 校准 · 发版基线）

> 本部分为**发版基线**，与第一部分同源；冲突时以本部分 + 《团队宪法》为准。
> 目的：新用户、新起项目、新会话一律按此执行；角色卡 / skill / 模板 / 宪法 / 铁律模板都必须与本节一致。
> Owner 2026-11-18 22:01 指令：全员修正自己的角色卡与角色卡模板、对齐工作流程并更新 skill；定位基础工作流；宪法模板与项目铁律模板同样以本工作流为准。

## A. 六角色职责与禁止事项（速查）

| 角色 | 核心职责 | 明确不做 | 验收权限 |
|---|---|---|---|
| 项目经理 PM | 建需求/任务、派单、催回执、记录 Owner 决定、组织验收材料、维护项目索引与准则、执行换人 | 不写需求正文/不做开发/不做测试结论；不替他人写业务文件 | **只能验收缺陷单**（`task accept --as pm`）；**不得验收需求** |
| 产品设计师 | 需求评审（RR）、范围/优先级建议、产品口径与模板内容评审 | 不写需求正文/不派单/不做测试结论 | 仅评审，不验收 |
| 需求分析师 | 需求正文唯一写者（`req write`）、需求分析、可测性依据 | 不评审自己写的需求、不派单 | 不验收 |
| 程序员 A / B | 实现与提交、自测、回执、修复缺陷 | 不改需求正文、不验收、不代其他角色回执 | 不验收 |
| 测试人员 | TR-Q 落库、独立复验、报告与证据、缺陷判定 | 不写需求正文/不实现/不派单 | 可验收缺陷单（`--as tester`）；**不得验收需求** |

## B. 验收权限（硬边界，程序已实现）

1. **需求级验收只能 Owner 本人**：界面「我的验收」点通过，或 Owner 终端 `owner --requirement <id> --action accept`。
2. **代管不改变验收权限**：有效代管只可代记**评审决定**（approved / rejected / skipped）；**需求验收、迭代、终止一律 Owner 本人**；任何角色/任何通道代需求验收都会被硬拦（`PROXY_ACCEPT_FORBIDDEN`）。
3. **PM 只能验收缺陷单**：`task accept --task <B-…> --as pm --evidence 报告:report --evidence 截图:screenshot --opinion …`；缺陷单验收与是否代管无关。
4. 测试人员同样可验收缺陷单（`--as tester`），但需求验收一律不得代。
5. 需求要到 `test_done` 才会出现在 Owner 验收列表；PM 的任务是**把材料准备齐**，不是替 Owner 点。

## C. 需求 / 缺陷 / 工具改动三条主流程

- **需求类**：Owner 目标 → PM 建需求→ 分析师写正文（G1）→ 产品评审 RR（G2）→（复杂需求）tester 落 TR-Q → **Owner 对当前正文落决定（G3）** → PM 派开发（G5 + 派单前置检查）→ 开发提交 → tester 独立复验（G7 + 证据两件套）→ 需求 `test_done` → **Owner 本人验收**。
- **缺陷类**：PM/任何角色立缺陷单（`type=bug`，必带 repro + 验收标准）→ PM 派开发 → 开发修复提交 → tester 复验（报告+证据）→ **PM 或 tester 验收缺陷单**。
- **工具/壳层/脚本/产出类**：直接改 + 提交 + tester 确认；跨边界/敏感改动先报 PM 定范围。

## D. 派单与环境纪律（本次发版新增/强化）

1. **派单前置检查程序门**：每次 `send --ack` 前必须 `dispatch-check`；`go`/`go_degraded` 才发；`queue`/`wait`/`wake_first`/`blocked` 先处置；强制必须 `--force --reason` 留痕。
2. **不打断在跑的角色**：目标 `running=true` 时不插单、不催；要插先记下、收工再发。判「是否在跑」以【会话排队】为准（running + lastEventAt），不以任务状态为准。
3. **测量窗口协同**：任何真窗口/Electron 测量前，先向 PM 报「需要干净窗口」；PM 协调其他角色停止各自 Electron 起停；测量后立即停手。
4. **工装安全（P0 硬规）**：任何角色、任何脚本、任何临时命令都**禁止**按进程名/路径/时间窗批量杀 electron（`Get-Process … | Stop-Process`、`taskkill /IM electron.exe`、`pkill`/`killall`）；**只允许** `taskkill /PID <自己 spawn 的 child.pid> /T /F` 或 `child.kill()`；无 PID 不杀；提交工装前跑 `node scripts/check-no-batch-electron-kill.cjs`。
5. **隔离口径**：界面/性能测量必须 `AWB_DATA_DIR` 独立实例 + 沙盘团队（`TEAM_ROOT` + `TEAM_SELFTEST=1`）；断言真实 `团队/状态/团队.json` 与 `data/userdata/workbench.json` sha256 前后不变；记录被测 HEAD 与启动 PID。
6. **机器负载口径**：测量报告必须记录同时段 electron 进程数与 CPU；负载异常（CPU 接近满/进程数异常）的测量结果只能作观测，不作门禁判据。
7. **口径变更纪律**：验收判据/口径以产品书面裁定为准，PM 不得口头放宽；确需调整先落文档（评估/裁定），并在报告里写明来源。

## E. 证据标准（所有角色执行）

1. 每条结论要有**可复跑命令 + 退出码 + 通过数/样本数**；写明被测 HEAD、隔离方式、启动 PID。
2. 证据"版本递增不覆盖"：更新证据用新版本名（报告-vN / 截图-vN），旧证据保留；报告里不得出现 `FAIL` / `不通过` / `未通过` 三词（门禁按严格关键词判），用「未达标项 / 豁免项 / 不合格项」表述。
3. 缺陷验收两件套：**报告（含 PASS/通过）+ 截图**；需求验收材料由 PM 汇总（报告 + 截图 + TR-Q/评审记录）。
4. Owner 书面豁免必须单独落文件（例：`项目经理/产出/v2.0-Owner书面豁免-…md`），报告引用该文件路径与数值。
