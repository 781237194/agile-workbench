# 团队工作流（从需求到收口）

> 这是团队执行顺序，不是建议。PM 必须按闸门推进，不能跳过回执直接叫下一批人。

## 总原则

- 一个工作区 = 一个项目；一个任务只有一个 owner。
- 一次只叫一个角色：`send --ack` 后 PM 停手，等对方 `ack`；未回执不派下一个。
- 没有回执 = 没发生；没有评审/签字/commit = 没完成。
- 只读任务需要的文件，不读全目录。
- 每次提交/回执一句话日志（对象 + 动作 + 单号/时间），不写长汇报。

## 阶段表

| 阶段 | 负责人 | 输入 | 动作/产物 | 闸门（必须满足才进下一阶段） |
|---|---|---|---|---|
| 0 接单 | PM | Owner目标/场景/边界/期限 | 写 `项目信息.md`；建需求/任务；定优先级建议 | Owner确认目标；项目信息已写 |
| 1 需求 | 需求分析师 | Owner/PM 的任务 | 在 `需求/R-YYYYMMDD-xxxx-标题.md` 写用户故事、边界、验收标准、异常；更新 `需求/00-需求总览.md` | 需求文件 + 验收标准；需求分析师提案 |
| 2 产品/架构评审 | 产品设计师 | 需求文件 | 评审需求；补流程/架构/数据流/失败回滚；给优先级建议；必要时更新产品/架构文档 | 产品在需求提案上 `review approve` 并回执 PM；需求分析师按意见更新 |
| 2.5 Owner评审（可选） | Owner ↔ PM | 需求更新文档 + 产品更新文档 | PM 必须在本轮弹出流程框让 Owner 选择：跳过评审 / 开始评审。Owner 开始评审后看文档、写意见、直接发 PM；PM 记录“通过 / 打回 / 跳过” | **Owner 必须作出一次明确选择**（跳过或通过）；打回则回需求/产品阶段；未选择不派发 |
| 3 派开发 | PM | Owner选择 + 产品 + 需求分析师回执 | 建 A/B 任务（带 requirementId、目标文件、验收）；一次只派一个 | PM 已收到 Owner 的跳过/通过记录 + 需求分析师+产品回执；A/B 各自 `ack + task claim` 后才派下一个 |
| 4 开发 | 程序员 A/B | 任务 + 需求 + 架构 | 写 staged → `propose`；互审；必要时接口/数据对账；PM 签字 apply | A/B 互审完成；跨模块对账记录；PM 签字 + apply |
| 5 测试 | 测试人员 | commit + 验收标准 | 独立跑 verify/用例；写测试报告；缺陷闭环 | 测试报告 + 证据；测试人员回执 PM |
| 6 收口 | PM | 程序员 A/B + 测试人员回执 | 确认任务 done；更新索引/看板；决定下一轮需求 | 程序员和测试回执都在；PM 才可进入下一轮 |
| 7 迭代 | PM | 测试结论/Owner反馈 | 新需求新建文件；澄清更新原需求；不把新需求塞旧文件 | 新需求重新走阶段 1 |

## 回执链

```text
Owner → PM：目标/边界
PM → 需求分析师：需求任务
需求分析师 → PM：需求文件 + 回执
PM → 产品：需求评审 + 架构任务
产品 → PM：评审结论 + 回执（需要时）
PM → Owner：需求更新文档 + 产品更新文档（路径/摘要）
Owner → PM：跳过 / 通过 / 打回 + 意见（PM 记录）
PM → 程序员 A/B：一次一个开发任务
A/B → PM：ack + claim + commit + 回执
A/B ↔ A/B：互审；跨模块对账
PM → 测试：commit + 验收标准
测试 → PM：测试报告 + 回执
PM → Owner/下一轮：收口结论
```

## A/B 之间什么时候对账

满足任意一条就必须对账，并把结论写进提案日志/测试说明：

- A/B 改同一个接口、数据结构、事件或配置文件；
- 一方依赖另一方的输出；
- 跨模块调用、权限、错误码、版本兼容；
- 任一方认为回归范围不确定。

只改各自独立文件、无共享接口时，可只互审，不额外对账；但要在回执里写明“无共享接口”。

## 文件路径纪律

- 所有交付文档必须写在**当前项目目录**内：PM 写 `项目经理/` + 根文档；产品写 `产品/`；需求写 `需求分析师/`；测试写 `测试人员/`。
- 程序员代码写**项目根代码目录**（默认 `site/**`，以《项目信息.md》为准），不得写进 `程序员A/` 或 `程序员B/`；角色目录只放设计、交接、回执、索引。
- 禁止写 `C:\Users\...\AppData\Local\Temp`、`%TEMP%`、桌面、C 盘根目录、用户 Home 根目录。
- 临时文件统一放项目 `_tmp/`，交付前删除；不得把临时目录当交付目录。
- 发现文件写到项目外：立即停手，报 PM，不得继续提交。

## PM 的硬闸门

1. 没写 `项目信息.md`，不叫角色。
2. 没收到需求分析师的回执，不叫产品评审。
3. 没收到产品评审回执，不派程序员。
3.5 本轮 Owner 没有明确选择“跳过/通过”（或打回后未重走）前，不派程序员；Owner 选择跳过时 PM 记录 skipped，不要求 Owner 每轮都评审。
4. 程序员 proposal 没互审、没签字，不 apply。
5. 没收到测试报告和回执，不把任务标 done。
6. 一次只发一个 `send --ack`；派单锁未清，不派下一个。

## 角色回执格式（一句话）

```text
角色 id + 任务 id + 已完成动作 + 产物/commit + 边界
```

例：

```text
analyst T-... 已完成 R-... 需求文件并回执；边界：未改产品/代码
tester T-... 已验收 commit C-...，3 项 PASS；边界：未改业务代码
```

## 失败即停

锁冲突、CAS 失败、评审/签字缺失、测试失败、回执缺失：停手报 PM，不绕过、不硬试到成功。
